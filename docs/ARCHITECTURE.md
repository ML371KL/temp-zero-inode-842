# Архитектура дашборда «MOEX Radar» (репо 842)

Дата: 2026-08-11. Дизайн под имеющуюся инфраструктуру: GitHub (repo `temp-zero-inode-842`) + Cloudflare Pages (`tzi-842.pages.dev`) + R2 (данные) + VPS 46.62.207.91 (вычислитель). Реализует четырёхслойную модель из `validation/REGIME.md`: эра → ядро-композит → машина состояний → мониторинг событий и потоков.

---

## 1. Принципы (выводы валидации, зашитые в дизайн)

1. **Дашборд — не сигнальная машина на каждый день, а машина состояний + медленный композит.** Ядро меняет знак ~2 раза в год; состояние меняется несколько раз в год. Значит: оперативность нужна не для скорости сигнала, а для (а) свежести картины, (б) событийных дней (ЦБ, ОРФР), (в) ворот риска (облигационный флаг). Интрадей — только витрина; официальный пересчёт — по закрытиям.
2. **Один писатель.** В R2 пишет только VPS. GitHub Actions — фолбэк-писатель, активируется ТОЛЬКО если хартбит VPS протух (лиз-объект в R2). Урок IBKR-аудита: два писателя = гонки.
3. **Канарейка внутри данных.** Каждый объект data.json несёт `generated_at`, `sources:{name:{asof, fetched_at, status}}`; фронт красит протухшие тайлы. Отдельно — сквозная проверка доставки (страница показывает возраст данных крупно).
4. **Честные лаги публикации** — те же, что в валидации: сигнал в панели датируется днём доступности (ОРФР +15, ИПЦ +13, Urals +5, декады +4). Никаких «подсмотренных» значений в витрине.
5. **Разделение «скоринг vs мониторинг».** Слои 1–2 дают числа и вердикты (валидированы). Слой 3 — только факты и графики, без предсказательных претензий (бейдж «monitor», как решено в VALIDATION.md).
6. **Модель может умереть.** Встроенный model-health: скользящий 24-мес IC композита; при уходе ниже нуля — статус «связи на этом окне не видно», плановая ревалидация — по критерию ×12 (§7).
7. **Позиция явная и одна** (аудит 02.09.2026). Панель не предлагает читателю собрать решение из ворот и наклона: `compute/decision.py` считает позицию «акции / деньги» сам — ворота с гистерезисом читаются ежедневно, наклон решается раз в неделю по дневному композиту с порогом ±0,2, исполнение на следующем закрытии — и кладёт её в `verdict.position` первой строкой витрины. Три прочтения знака в одном продукте давали просадку от −26 % до −34 %.

## 2. Топология

```
[Источники] ──> VPS (питон-пайплайн, systemd-таймеры)
                 │  fetch/ (кэш сырья в R2: raw/{source}/...)
                 │  signals (панель → композит → состояния → тайлы)
                 │  publish (лиз → data.json, history/*.json в R2)
                 │  alerts (Telegram при сменах состояний/знаков)
                 ▼
        R2 bucket moex-radar
                 ▲                        ▲
    GH Actions (фолбэк-писатель,          │
    активен только при протухшем лизе)    │
                                          │
Cloudflare Pages tzi-842 ── functions/data/[[path]].js ── читает R2
Браузер ── статический фронт ── /data/data.json (+ history шарды)
cron-job.org ── (1) пинг VPS-эндпоинта живости, (2) триггер fallback-workflow при протухании
```

- **VPS — primary compute.** Уже держит IBKR-пайплайн; добавлены шесть пар юнит+таймер `moex-radar-*.timer/service` (обвязка `/usr/local/sbin/moex-radar` → `pipeline/run.py --mode=...`). Без venv — намеренно: у пайплайна нет ни одной зависимости вне стандартной библиотеки (§3), достаточно системного `/usr/bin/python3` 3.12+. Все RU-источники отвечали в тестах на зарубежный IP (проверено из Малайзии) — но проверка с ноутбука оказалась недостаточной: с VPS часть хостов ведёт себя иначе (docs/LATENCY.md §4); на случай геоблока каждого фетчера — фолбэк-цепочка (см. §4).
- **GitHub repo 842**: код пайплайна, фронт, `inputs/` (ручные вводы), workflows (deploy Pages; fallback-pipeline по cron+dispatch; recalibrate quarterly). Данные в git НЕ живут (только в R2) — кроме `inputs/` и снапшота `validation/` (замороженные артефакты исследования: panel_long, ic_results, VALIDATION/REGIME.md).
- **R2 структура** (фактическая, пишет `pipeline/publish.py`):
  - `data.json` — горячий компакт (≤250 КБ, `publish.MAX_BYTES`; при переборе payload режется лестницей `TRIM_STEPS`: спарклайны → ряды тайлов → глубина истории → события): всё для первого экрана.
  - `history/daily.json` — дневные ряды для графиков (IMOEX, RGBI, MCFTR, RVI за 2 года полно + помесячно раньше; композит и лента состояний целиком).
  - `history/monitors.json` — лента заголовков тайлов слоя 3 (одна запись на смену asof/заголовка, до 200 на тайл).
  - `raw/{series_id}.json` — зеркало нормализованных рядов стора (не «сырьё по датам»: один объект на ряд, контракт §1) + `raw/_index.json` — манифест зеркала, без которого стор нельзя восстановить на пустой машине (`lib/mirror.py`).
  - `lease.json` — `{writer, holder_id, heartbeat, ttl_seconds}` (контракт §5). Отдельного `events.log` НЕТ: события живут в `data.json.events` (последние 20) и в телеграме/ленте NEXUS.

## 3. Вычислительное ядро (pipeline/)

Портируется из `validation/` (тот же код, отрефакторенный в модуль):

- `panel.py` — инкрементальная сборка длинной панели: дочитывает только новые дни из raw-кэша, пересчитывает хвост сигналов (rolling-окна требуют максимум 504 дня хвоста — полный пересчёт панели всё равно секунды, можно и не оптимизировать).
- `core.py` — слой 1: z-скоры (rolling 60м, clip ±3) → композит = mean(z(usd_mom63), z(slope_10_2) [, −z(urals_rub_gap) — флагом, по умолчанию вкл. с бейджем «не защищена»]). Гистерезис знака ±0,1 для алертов.
- `states.py` — слой 2: сырые биты — тренд (close vs MA200), вола (21д реализованная > P80 за 756д), облигации (RGBI dd < −4%), фаза ставки (знак последнего изменения); на них стоят ячейка, замороженная статистика CELL_STATS и лента. Поверх — ворота с ГИСТЕРЕЗИСОМ (`states.gate`: вола вкл. > p80 / выкл. < p60, RGBI флаг < −4% / снятие > −3%, тренд ±2% от MA200; `constants.DECISION`) и три режима (`constants.REGIMES`: «ворота закрыты», «стресс, ворота открыты», «спокойный рынок») со статистикой по закрытым месяцам в двух мерах — по цене и над кэшем (`regime_stats`). Активные сигналы второго ряда — пять (mom63 в стрессе/медведе, dd252 в медведе, switch_spread в смягчении, dy_trail после 2022, rgbi_mom21 в медведе); rb_gap и futoi_z120 сняты аудитом 02.09.2026.
- `decision.py` — слой решения (аудит 02.09.2026, ступень P2): дневной композит «как compute_core любым днём» (`daily_composite`, на концах месяцев совпадает с `monthly_frame` ≤1e-9), дни решения = последний торговый день недели, знак с гистерезисом ±0,2 только в день решения, автомат позиции `run_automaton` (выход по воротам любым днём, по наклону — в день решения; вход любым днём), `verdict.position` с причиной, условиями смены, историей RLE с 2004 и ставкой кэша; `position_prev_rule` — прежнее правило для сравнения. Эталон — `validation/audit-2026-09/impl/decision_fixture.json`, побитово (`tests/test_decision.py`).
- `shadow.py` — тень: сигналы под наблюдением 12 месяцев (репрайсинг ожиданий на конце месяца, курс к MA200, долларовая бочка, HI2, ранний бит ширины, блок «розничная эра») и теневая позиция «пакет + бит репрайсинга». Только стандартная библиотека, каждый сигнал в своём try, история пишется в стор рядами `shadow_<id>`; на позицию не влияет и прогон уронить не может (run.py оборачивает в try, при ошибке — `shadow.error`).
- `monitors.py` — слой 3: тайлы без скоринга (см. §5).
- День ЦБ — БЕЗ отдельного модуля и режима (`compute/events.py` из ранних набросков не существует): `key_rate` стоит в `registry.MODES["intraday"]` и опрашивается каждые 5 минут SOAP-запросом (`cbr._keyrate_soap`, ~2 КБ ответа), так что решение 13:30 МСК доезжает за один такт; вердикт «сюрприз/в линию» против `inputs/consensus.yml` даёт `alerts.py` (событие `cb_decision`).
- `health.py` — model-health (trailing 24м IC композита по факту): `ok` / `warn` («связи на этом окне не видно») / `review` (двенадцать закрытых месяцев подряд ниже нуля, §7); канарейки источников, SLA.
- `publish.py` — сборка data.json/history, захват лиза (CAS: читает lease, пишет со своим id, перечитывает), запись, обновление heartbeat.
- `alerts.py` — телеграм по образцу notify.mjs 837/838 (события: см. §6).

Всё — Python 3.12, **только стандартная библиотека**: ни pandas, ни requests, ни venv (контракт §0). Запрет не на честном слове — его держит шаг CI «Пайплайн остался на стандартной библиотеке» (`.github/workflows/ci.yml`): голый setup-python без установки зависимостей, первый же посторонний import валит сборку. Почему так: пайплайн обязан запускаться на любой машине (VPS, раннер GHA, ноутбук) одним системным python3. Полный дневной прогон 19–31 с, интрадей 3,6–5,4 с (замеры — docs/LATENCY.md §1).

## 5. Фронт (Cloudflare Pages, статика + functions/data-прокси в R2)

Один экран, сверху вниз (после аудита 02.09.2026):

0. **Строка котировок** — контекст, не сигналы.
1. **Позиция** — ПЕРВАЯ строка панели: «ПОЗИЦИЯ: АКЦИИ / ДЕНЬГИ», с даты, причина; во флэте — ставка денег (вклады топ-10), дата следующего решения по наклону (пятница), знак решения, «что изменит позицию» (условия с расстояниями до порогов), «исполнять на следующем закрытии», лента «акции и деньги с 2004». Тон: «акции» — акцент `--accent`, «деньги» — чернила; не красный/зелёный — позиция не оценка. Старая витрина без `verdict.position` блок не рисует.
2. **Шапка: ворота и наклон**: три бита с гистерезисом (`states.gate`, «с даты») + фаза ставки; вместо ячейки — режим из трёх с его статистикой по закрытым месяцам в двух мерах (по цене и над деньгами: медиана, среднее, доля плюсовых; n и 95 % интервал мелко); наклон −3…+3 с подписью от позиции (не от знака дневного числа), под шкалой — «решение по пятницам, порог ±0,2; знак решения с даты», закрытый месяц справочно мелко. Правило дня.
3. **Слой 1 — ядро**: три компонента (z, спарклайн 2 года, подпись механизма), композит-лента с 2004 (фон = знак), отметки смен знака; здоровье модели (IC 24м, интервал, статус ok/«связи не видно»/ревалидация, порог ×12).
4. **Слой 2 — машина состояний**: лента ячеек с 2004 (по сырым битам), расстояния до переключения — до порога, который сработает следующим (у включённого флага порог ВЫКЛЮЧЕНИЯ), активные сигналы второго ряда (пять), таблица восьми сочетаний со статистикой исследования (в шапке их больше нет).
5. **Слой 3 — мониторы** (16 тайлов, порядок `monitors.BUILDERS`): цена ожиданий по ставке (y1 − ключ, Δ21, RUSFAR3M − ключ, y0.5 − ключ; вместо снятого недельного ИПЦ), заседание ЦБ (со строкой недельного ИПЦ за 4 недели), потоки ОРФР, FUTOI (monitor, без вердикта), спред ВДО, рублёвая бочка (единственная), вклады против дивидендов (единственный спред), дивкалендарь, аукционы ОФЗ, RVI, ширина (monitor), Polymarket, сентябрьский узел (даты живут только в `constants.SEP_NODE`), LQDT, малые каппы, частные инвесторы.
6. **Тень** — отдельный раздел «считается, копит историю, на позицию не влияет»: пунктирные карточки сигналов (значение с единицей, бит «включён/выключен» чернилами, дата, нота, мини-история 24 мес) и карточка теневой позиции «если бы бит репрайсинга был в решении». Без `shadow` в payload раздел не рисуется.
7. **Журнал**: лента алертов/смен состояний/позиции/событий.
8. **Таблица** (по кнопке): позиция и ворота на дату, компоненты ядра, помесячно композит / ячейка / ворота с гистерезисом / позиция за 36 месяцев.

Фронт без сборщика (vanilla JS + лёгкий чарт, как в 837/838), тёмная тема, mobile-first (пользователь смотрит с телефона).

## 6. Алерты (Telegram, по образцу notify.mjs)

Шлются при СМЕНЕ, не по расписанию:
0. Смена позиции (`position_change`): «Позиция: акции → деньги» / «деньги → акции», причина словами (ворота закрылись: какой флаг; наклон ниже/выше порога; ворота открылись), «исполнять на следующем закрытии»; первый прогон молчит. Отдельный слой, в семью режимов не сливается.
1. Композит пересёк 0 (с гистерезисом ±0,1) — «ядро развернулось» (оставлено как событие наклона).
2. Смена ячейки состояния; отдельно выделенно — установка/снятие облигационного флага и вход в «окно покупки» (вола=1, облигации=0).
3. День ЦБ: решение vs консенсус (довиш/хокиш/в линию) + напоминание за день «внеси консенсус».
4. ОРФР вышел: сводка потоков + метрика исчерпания ДУ.
5. Провал аукциона ОФЗ; первая декада роста ставок вкладов после серии снижений.
6. Санитарные (только пользователю, не в канал): протухание источника сверх SLA, потеря лиза, здоровье модели в статусе review (`health_review`: IC-24 ниже нуля двенадцать месяцев подряд; прежние `health_dead`/`health_review_due` объединены).

## 7. Надёжность и эксплуатация

- **systemd** на VPS: `moex-radar-intraday.timer` (5 мин, 10:00–00:00), `moex-radar-daily.timer` (19:05, 23:55), `moex-radar-monthly.timer` (12:00, 18:00 и 22:30 — поллинг окон публикации). Уроки claude-remote/systemd учтены: абсолютные пути, системный python3 без venv (зависимостей нет — §3), `Restart=on-failure`.
- **cron-job.org** (существующий аккаунт): (1) каждые 30 мин GET `https://tzi-842.pages.dev/data/data.json` → если `generated_at` старше 2 ч в торговое время — дёргает GitHub `workflow_dispatch` fallback-pipeline (тот же код, но пишет только при протухшем лизе). ⚠️ PAT Actions:write истекает ~окт-2026 — общий с BTC-дашбордом риск, обновить один раз для всех.
- **CI**: тесты на фиксированных датах (никаких «сегодня минус N»), инварианты схемы data.json, смок парсеров на замороженных фикстурах страниц; ревью диффа перед пушем — обязательная практика.
- **Реколибровка**: `ops/recalibrate.py`, юнит `moex-radar-recalibrate` (5-е число каждого месяца, 21:30 UTC) + `.github/workflows/recalibrate.yml` (ручной запуск) — пересчёт инварианта композита, здоровья, статистики ячеек, слоёв и условных IC на удлинённой истории; отчёт-диффом в сводку прогона и в PR. Скрипт не меняет ни одного числа. Считает ежемесячно, а ГОВОРИТ по-разному: расхождение и достигнутый порог §7 уходят в ops-канал сразу, рутинное «расхождений нет» — только в квартальные месяцы (январь, апрель, июль, октябрь), чтобы ежемесячное подтверждение не приучило не читать эти сообщения. На пустом раннере стор восстанавливается из зеркала `raw/` в R2 по манифесту `raw/_index.json`; на VPS работает по локальному стору. Годовая полная ревалидация — отдельно, руками. Пороговое правило пересмотра состава ядра — критерий ×12 (аудит 02.09.2026): только при model-health<0 ДВЕНАДЦАТЬ закрытых месяцев подряд И наличии механизма у кандидата (не по трейлинг-IC — этот путь доказанно ведёт в шум). Прежний порог «два квартала» срабатывал бы на шуме: при окне 24 месяца серии 6–9 месяцев ниже нуля случались на истории у РАБОЧЕЙ модели, а ложная тревога дороже опоздания. Длительность «ниже нуля» измеряется (`core.health.below_zero_months`, порог `constants.HEALTH_REVIEW_MONTHS` = 12); при её достижении статус здоровья становится `review` (статуса `dead` больше нет: IC<0 на таком окне неотличим от нуля, se≈0,21) и в ops-канал уходит ОДНО событие `health_review` (прежние `health_dead` и `health_review_due` упразднены — первый приходил на первый же месяц ниже нуля). Протокол по порогу — «реколибровка, не сокращение позиции»: позиция панели (`verdict.position`) продолжает вестись по действующему правилу, а состав ядра пересматривает человек по отчёту реколибровки; панель ни веса, ни ноги сама не меняет.
- **Первичное наполнение**: raw-кэш заливается из `validation/data/` (уже скачанные 2004–2026) — пайплайн со дня 1 работает в инкрементальном режиме.
